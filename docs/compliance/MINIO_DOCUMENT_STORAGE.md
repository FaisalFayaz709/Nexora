# MinIO Document Storage

## Purpose

The implementation replaces the previous placeholder document storage behavior with a real backend-controlled MinIO integration while preserving the locked NEXORA architecture.

The blueprint requires private object storage through MinIO, backend-mediated upload/download authorization, checksum/object validation, document metadata, versioning, and retention-aware deletion. Business modules must never call MinIO directly; they must call the centralized backend `StorageService`.

## Locked stack compliance

This implementation does not change the approved stack:

- Frontend: Next.js + TypeScript
- Backend: Fastify + TypeScript
- Database: PostgreSQL + Prisma
- Storage: MinIO
- Queue/cache: Redis + BullMQ
- Runtime: Docker Compose + Nginx
- Workspace: single TypeScript monorepo with root dependency management

No Express, NestJS, MongoDB, Firebase, Supabase, TypeORM, Sequelize or alternate storage provider is introduced.

## Architecture compliance

The storage SDK is allowed only inside `backend/src/core/storage`. Business modules use `StorageService`; they do not import the MinIO SDK.

Required boundary remains:

```text
Controller -> Service -> Repository / StorageService
```

The documents module still uses:

- `DocumentService` for business orchestration
- `DocumentRepository` for Prisma persistence
- `StorageService` for object storage
- `AuditWriter` for business audit events

## Implemented controls

### Upload intent

`POST /api/v1/documents/upload-intent` now produces a real MinIO presigned PUT URL through `StorageService.uploadIntent`.

The object key is generated by the backend and follows the tenant-scoped pattern:

```text
organizations/{organizationId}/documents/{subjectType}/{subjectId}/{category}/{yyyy}/{mm}/{uuid}-{safeFileName}
```

The client cannot choose an arbitrary bucket or tenant path.

### Complete upload

`POST /api/v1/documents/complete-upload` now verifies the uploaded object before metadata is committed:

- object key must be under the authenticated tenant prefix
- object must exist in the private MinIO bucket
- stored object size must match the completion request
- SHA-256 checksum is verified when `DOCUMENT_ENFORCE_OBJECT_CHECKSUM=true`
- document and version rows are created only after storage verification succeeds
- document completion creates an audit event

### Download URL

`GET /api/v1/documents/:id/download-url` now generates a real MinIO presigned GET URL after:

- authentication
- tenant resolution
- document permission check
- tenant-scoped DB lookup
- access log creation
- tenant-prefixed object key validation

The file remains private in MinIO; access is time-limited and backend-authorized.

### Versioning

New document versions are verified against MinIO before a `DocumentVersion` row is appended. Previous versions are retained.

### Database metadata

`DocumentVersion` now includes `bucketName` so the database stores both bucket and object key, matching the blueprint's object metadata requirement.

## Environment variables

```text
MINIO_ENDPOINT=http://minio:9000
MINIO_ACCESS_KEY=nexora-local
MINIO_SECRET_KEY=change-me-local-only
MINIO_PRIVATE_BUCKET=nexora-private
MINIO_PUBLIC_BUCKET=nexora-public
MINIO_UPLOAD_URL_TTL_SECONDS=900
MINIO_DOWNLOAD_URL_TTL_SECONDS=300
DOCUMENT_MAX_UPLOAD_BYTES=52428800
DOCUMENT_ENFORCE_OBJECT_CHECKSUM=true
```

## Runtime validation required locally

This implementation is source/static complete. Full runtime proof requires local execution after the runtime foundation lockfile generation:

```bash
pnpm verify:static
pnpm install --frozen-lockfile
pnpm db:validate
pnpm db:generate
pnpm db:migrate:deploy
docker compose up --build
```

Then verify:

1. Upload intent returns a MinIO presigned URL.
2. Uploaded object exists in `nexora-private`.
3. Complete upload fails if checksum/size/object key is wrong.
4. Complete upload succeeds when object exists and checksum matches.
5. Cross-tenant object key cannot be completed or downloaded.
6. Download URL is issued only after DB permission and access log checks.

## Not included in the current implementation

the current implementation does not implement PDF generation, malware scanning, email dispatch, report exports or document-expiry scheduled jobs. Those remain in the BullMQ/document/reporting passes.
